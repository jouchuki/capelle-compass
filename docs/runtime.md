# Runtime and deployment

For the complete infrastructure and release process, see the
[deployment runbook](deployment.md). The [architecture document](../ARCHITECTURE.md)
explains the application components and data flows.

## Application

Compass supports municipal research and jeugdzorg analysis. The backend serves
the frontend build from `frontend/dist` and stores sessions in its configured
database.

## Bundled research tools

The research source, skills, and small reference fixtures are included in `agent/`.
Install and check them from the Compass repository root:

```bash
make install-agent
make check-agent
```

This installs eight Python projects and ten CLI commands in `.venv-agent/`.
See the [research runtime inventory](../agent/README.md) for the skills, data,
auxiliary dashboards, optional scraper dependencies, and source provenance.

For a new local installation, `make init-local` creates `backend/.env` with
absolute paths to this checkout's `agent/`, `agent/jeugdzorg/`, `.agent-home/`,
and `.venv-agent/bin/`. It preserves its refusal to overwrite an existing file.
If a local `.env` already exists, update these runtime settings there to absolute
paths for this checkout while preserving its secrets:

| Setting | Repository location |
| --- | --- |
| `CAPELLE_OHRS_WORKING_DIR` | `agent/` |
| `CAPELLE_OHRS_WORKING_DIR_JEUGDZORG` | `agent/jeugdzorg/` |
| `CAPELLE_OHRS_HOME_DIR` | `.agent-home/` |
| `CAPELLE_OHRS_TOOLS_BIN` | `.venv-agent/bin/` |
| `CAPELLE_OHRS_JOBS_DIR` | A writable per-job artifact directory |

## External services and large corpora

Real analysis still requires OHRS, a configured model provider, and the data
sources needed for the question. `scripts/fetch-ohrs.sh` downloads the pinned
OHRS release; set `CAPELLE_OHRS_BINARY` to the installed executable. Configure
provider/model settings under `.agent-home/.openharnessrs/settings.json` and
supply credentials through the operator's runtime environment. That directory
is ignored by Git. Workspace settings in `agent/.openharnessrs/` retain the
research tool permissions; per-job callbacks are generated by the backend.

The bundled youth-care workspace includes its skill and three synthetic CSVs.
Municipal survey, budget, citizen-report, and CBS metadata snapshots are also
included. The larger national corpora are populated separately in
`data/groeikernen/`; `agent/data` points there through a repository-relative link.
Use the download/preparation scripts in `scripts/` to populate the required
municipalities. Do not treat an empty coverage result as evidence that a policy
or dataset does not exist.

Policy semantic search requires a populated Chroma index and embedding-provider
access. Configure `CAPELLE_CHROMA_HTTP` for the intended service and provision
its index separately. For local indexing, policy acquisition writes to
`data/policy-pdfs/` (`CAPELLE_POLICY_PDF_ROOT` overrides it). The agent tools can
use a local Chroma index when run directly without an HTTP setting.

`make check-agent` is an offline installation check. It does not validate live
model access, external APIs, Chroma coverage, or end-to-end analysis execution.

## Production configuration

Build the frontend with `make build`, install backend requirements in a dedicated
environment, and start `python -m capelle_platform.main` from `backend/` under your
process manager. Configure an explicit HTTPS `CAPELLE_PUBLIC_ORIGIN`, secure
cookies, debug off, and strong JWT and internal-hook secrets. Forward the
public domain to the backend. Email links use the canonical public origin.

For multiple backend processes, provision a Postgres database,
RabbitMQ virtual host, credentials, and job/runtime directories. Configure
`CAPELLE_STORE=postgres`, `CAPELLE_QUEUE=rabbitmq`, and `CAPELLE_WS_HUB=rabbitmq`
with their corresponding DSN/URL. Use a dedicated RabbitMQ virtual host for the
application. Plan database migrations and queued-work handling before changing
a production deployment.
